## Required capabilities

Run the supervisor on Node.js 22.13 or newer. The current v3 controller path additionally requires OpenClaw 2026.8.1+ and the installed, enabled, Gateway-loaded `acp-lifecycle-guard` 0.6.0+ plugin exposing `acp_report_controller`; that plugin's package engine requires Node.js 22.22.3+. Installation alone is not activation. The production host transport is POSIX-only and requires an available tmux executable plus an executable regular `/usr/bin/env`; the transport uses `env -i` to prevent stale tmux-server environment variables from entering the runner. The Claude canonical launcher `claude-acp-launcher.mjs` additionally requires a runtime with POSIX `process.execve`: Node.js 22.15 or newer within the 22.x line, 23.11 or newer within the 23.x line, or any later release line (24+). Node.js 23.0–23.10 is newer than 22.15 but lacks `process.execve`. The launcher is POSIX-only — `process.execve` does not exist on Windows. Support is capability-detected: any runtime or platform without a `process.execve` function fails closed with `execve_unsupported`.

Resolve ACPX from the explicit package root recorded in `runtimeModule`. That path is machine-resolved by the [runtime-module preflight](#runtime-module-preflight) from the active OpenClaw plugin's read-only dependency information before launch — never hand-copied or chosen by the caller. The supervisor does not execute discovery commands. Require public equivalents of:

- `createAcpRuntime`
- `createRuntimeStore`
- `createAgentRegistry`
- runtime `ensureSession`, `startTurn`, and `close`
- a turn with matching `requestId`, async `events`, Promise `result`, `cancel`, and `closeStream`
- distinct `completed`, `cancelled`, and `failed` results

Use capability detection. Do not select behavior from a version string alone.

## Compatibility targets

Require the ACPX 0.11.2-or-newer turn capability contract. Older releases such as ACPX 0.5.3 do not expose `startTurn`, `turn.result`, `closeStream`, or `onPermissionRequest` and must fail closed. OpenClaw releases pin different ACPX versions, so inspect the active plugin instead of assuming compatibility from the OpenClaw version. The initial tested matrix covers ACPX 0.11.2 and the standalone forward target ACPX 0.13.0.

A target passes only when the same behavior tests confirm runtime discovery, permission inspection, foreground rejection, normalized event consumption, response capture, exact result mapping, cancellation, cleanup, and process exit.

Fail closed on incompatible capability changes. Never fall back to another ACP route.

## Runtime-module preflight

`runtimeModule` is machine-resolved. The canonical pre-start path is `scripts/acpx-runtime-preflight-cli.mjs` (module `scripts/acpx-runtime-preflight.mjs`), which reads exactly one absolute owner-private JSON input file behind `--input` — the same private-file contract as every other operator CLI in this skill (no symlink, a regular file with no group or world permissions on POSIX, bounded size). Its closed actions under schema `acpx-runtime-preflight.v1` are `attest` and `assemble`; a new run preparation must go through both, and the caller never hand-copies or chooses `runtimeModule`.

`attest` (`pluginInfoFile`, `attestationFile`) consumes the raw JSON document that `openclaw plugins info acpx --json` prints on stdout, saved by the operator to a private owner-only file exactly as printed — the document is used directly and is never reshaped, filtered, or hand-edited by the caller. Selection is exact and fail-closed against that raw schema:

- the raw `plugin.dependencyStatus.dependencies` array must contain exactly one entry whose `name` is exactly `acpx` — a missing exact match fails `plugin_info_dependency_missing` and more than one fails `plugin_info_dependency_duplicate`; a scoped name such as `@openclaw/acpx`, a cased spelling, or a prefix/suffix variant is never a match;
- that entry's `resolvedPath` must be an absolute bounded well-formed path (`plugin_info_resolved_path_invalid` for a relative, empty, over-length, or malformed value);
- the active plugin package root is bound from the raw fields that carry it: `plugin.rootDir` is mandatory and the optional top-level `install.installPath` (null for a non-npm install) is bound too when present; a resolved path equal to either root fails `plugin_info_plugin_root_selected`, and a document whose `plugin.rootDir` (or a present `install.installPath`) is missing, relative, or malformed fails `plugin_info_plugin_root_invalid` — schema drift never weakens the root gate;
- any other drift from the raw schema fails closed with a bounded code: a document without a `plugin` object fails `plugin_info_invalid` — including the legacy synthetic shape that carried a top-level `dependencies` array with top-level `path`/`root`/`packageRoot` keys, which the real command never printed and which is deliberately rejected so hand-reshaping the JSON is never an alternate contract — and a missing or malformed `plugin.dependencyStatus` or dependency entry fails `plugin_info_dependencies_invalid`; an unreadable or non-private input file fails `plugin_info_file_invalid` / `plugin_info_file_json`.

The selected package is then validated before any attestation is written:

- a real non-symlink package root (`runtime_package_root_missing`, `runtime_package_root_symlink`, `runtime_package_root_not_directory`) with a readable `package.json` (`runtime_package_json_missing`, `runtime_package_json_invalid`);
- the manifest `name` must be exactly `acpx` — `runtime_package_name_invalid` rejects the `@openclaw/acpx` plugin package as defense in depth behind the raw `plugin.rootDir` binding, so the mistaken-plugin-root selection stays blocked even if the root were reached through a path spelling the root comparison missed;
- a plain release `version` (`major.minor.patch`, `runtime_package_version_invalid` otherwise) of at least 0.11.2 (`runtime_package_version_unsupported`);
- a real non-symlink regular `dist/runtime.js` entry (`runtime_entry_missing`, `runtime_entry_symlink`, `runtime_entry_not_regular`, `runtime_entry_unreadable`);
- capability detection stays authoritative — the version gate alone is never sufficient: the entry is imported (`runtime_entry_unloadable` on failure) and must export `createAcpRuntime`, `createRuntimeStore`, and `createAgentRegistry`, enforced by the supervisor's own capability check with the same `acpx_runtime_capability_missing_*` codes.

Success writes the owner-private attestation artifact, schema `acpx-runtime-attestation.v1`, with owner-only permissions and exactly once per path (`runtime_attestation_exists`, `runtime_attestation_write_failed`). It carries the validated absolute `runtimeModule`, the `runtimeVersion`, SHA-256 content digests of `package.json` and `dist/runtime.js`, and `issuedAtMs`. The attestation is owner-private evidence: it necessarily contains the resolved path and must never enter Discord output, a watchdog payload, or any public artifact.

`assemble` (`attestationFile`, `configFile`, `outputFile`, optional `maxAttestationAgeMs`) supplies the attested module to the run config and fails closed when the attestation is:

- absent — `runtime_attestation_missing`;
- invalid — any filesystem, permission, size, JSON, or shape violation is `runtime_attestation_invalid`;
- stale — older than the bounded freshness window (`runtime_attestation_stale`; `maxAttestationAgeMs` defaults to `600000` and is bounded to `1000`–`3600000`, out-of-bounds values fail `invalid_preflight_max_age`; an issue instant more than one second ahead of the clock fails `runtime_attestation_future`);
- mismatched — a fresh static inspection of the attested package must still match byte-for-byte: a changed digest or version fails `runtime_attestation_mismatch`, and a package that degraded structurally fails with its own static `runtime_package_*` / `runtime_entry_*` code.

Only then is `outputFile` written, exactly once (`config_output_exists`, `config_output_write_failed`), as the owner-prepared draft `configFile` with `runtimeModule` replaced by the attested path. Any pre-set draft value — including the template sentinel — is replaced, so the caller never chooses the module. The assemble step is deliberately narrow: it changes only `runtimeModule`, and the supervisor's config loader remains the authoritative validator of the assembled config. Draft-file problems fail `config_draft_file_invalid`, `config_draft_file_json`, or `invalid_config_draft`.

CLI evidence is bounded on both streams: success writes one `runtime_preflight_result` event to stdout (`status` `runtime_attested` or `config_assembled`, plus the runtime version), and every failure writes exactly one `runtime_preflight_error` event with a bounded stable code to stderr and exits with the invalid-config code `64`. No event ever carries a path, plugin-info payload, or free text. Input-shape violations use the bounded codes `usage`, `invalid_input_file`, `invalid_input_file_missing`, `invalid_input_json`, `invalid_preflight_input`, `invalid_preflight_schema_version`, `invalid_preflight_action`, `invalid_preflight_plugin_info_file`, `invalid_preflight_attestation_file`, `invalid_preflight_config_file`, `invalid_preflight_output_file`, and `invalid_preflight_max_age`.

`templates/supervisor-config.json` ships `runtimeModule` as the non-absolute sentinel `RUNTIME_MODULE_FROM_PREFLIGHT` on purpose: a config prepared from the template without the assemble step fails the supervisor's own loader (`invalid_runtime_module_not_absolute`) instead of running a hand-chosen module. Backward compatibility is preserved without a supervisor contract change: an already-prepared config carrying a previously validated absolute `runtimeModule` remains valid unchanged, and the supervisor keeps its own load-time and import-time runtime checks (`invalid_runtime_module*`, `acpx_runtime_module_*`, `acpx_runtime_capability_missing_*`) as the last line of defense.

## Private input and output

The supervisor and Claude launcher accept only one command-line value: an absolute private config-file path. Production callers invoke `acp-host-transport-cli.mjs` with one absolute owner-private input file. Its closed actions are `probe`, `prepare`, `activate`, `status`, `claim-report`, `begin-delivery`, `ack-report`, `cancel`, and `reconcile`; every action has an exact-key JSON shape under schema `acp-host-transport.v2`. `status` optionally accepts `afterSequence`, `serviceCursorAck`, or the bounded recovery flag `reissueServiceCursor`; `claim-report` requires `jobId`, `runToken`, and `destination`; `begin-delivery` requires `attemptId` and `fence`; `ack-report` requires `reportId`, `reportKind`, `cadence`, `attemptId`, `fence`, the structured canonical `report`, and `receipt`. The `acp-host-transport.v2` schema is an incompatible bump: the private record carries the fenced publication-attempt state and acknowledgement requires the attempt identity, so `acp-host-transport.v1` inputs and records fail closed with the standard schema/record codes — complete or cancel an in-flight v1 run with the v1 skill before upgrading. After launch, the only accepted supervisor stdin control is one bounded host-activation record described in [Host activation and lifecycle ledger](#host-activation-and-lifecycle-ledger); it carries the exact tracked host-process handle and is never emitted publicly.

The config points to a separate private prompt file and a response-file path that must not exist yet. Reject config or prompt symlinks. On POSIX systems, config and prompt files must have no group or world permissions. Require an existing state directory to be a real directory with owner-only permissions; do not repair broad permissions by changing them.

The supervisor writes the model response to the response file with owner-only permissions. Raw response text is not included in normalized progress events. The owner-only state directory also receives one `supervisor-<runId>.lifecycle.json` ledger for the run; it contains host tracking evidence and must never be copied into a public watchdog payload.

## Config fields

Required:

- `agent`: canonical ACP agent name from the closed supported set: `claude` or `codex`. The closed set is enforced by one centralized gate with two stable codes, and that gate runs first on both paths: in the loader it runs before the working directory, prompt file, response path, state directory, or runtime module is ever touched, and in the in-memory `runSupervisor` path it runs before every other preflight, so a config assembled without the loader fails with the same codes and there is no order-dependent asymmetry between agents. ACPX normalizes agent names with trim/lowercase, so a spelling such as `Claude` or `Codex` would still resolve to the same adapter while bypassing every exact-match gate; any spelling that normalizes to a supported agent other than the canonical lowercase value is rejected as `invalid_agent_not_canonical`, and an agent outside the closed set is rejected as `invalid_agent_unsupported` (invalid-config exit through the loader, supervisor error exit through the in-memory gate). The public presentation mapping is closed and fail-closed — `claude` is presented as `Claude Code` and `codex` as `Codex` on every reporting template, and a caller can never choose or introduce a label through config data. The pure reporting contract keeps its own `invalid_reporting_agent` boundary code where the contract itself is the surface: a validation context binding an agent outside the closed mapping when the validator (or the standalone `runReportingPreflight` backstop) is invoked directly, and a v2 bundle whose `agent` attestation does not equal the canonical config agent
- `cwd`: absolute working directory
- `sessionKey`: unique task identity
- `promptFile`: absolute existing private file
- `responseFile`: absolute new private file
- `stateDir`: absolute private runtime state directory; before runtime loading the supervisor creates one owner-only host lifecycle ledger beneath this directory
- `runtimeModule`: absolute ACPX package root or runtime module file. New preparations obtain this value only through the [runtime-module preflight](#runtime-module-preflight) `assemble` action; already-prepared configs carrying a previously validated absolute path stay valid
- `allowKinds`: non-empty tool-kind allowlist that excludes the unclassified `other` kind
- `timeoutMs`: positive turn deadline independent of watchdog cadence; the template ships a two-hour emergency ceiling, configurable per run
- `lifecycle`: start-receipt contract binding the run to the control conversation
  - `lifecycle.controlConversationId`: control conversation identifier
  - `lifecycle.startReceipt.conversationId`: conversation the start message was delivered to
  - `lifecycle.startReceipt.messageId`: delivered start-message identifier
  - `lifecycle.startReceipt.deliveredAt`: caller-observed delivery instant
- `reporting`: mandatory public reporting bundle, current schema `acp-reporting-v3` (`acp-reporting-v2` and Claude-only v1 remain bounded migration inputs), bound to the canonical `agent`, control conversation, lifecycle receipt, and deterministic report-controller job structure; see [Reporting contract](#reporting-contract)
- `auth` (required exactly when `agent` is `claude`): Claude credential declaration
  - `auth.kind`: must be `claude-setup-token-env-file`
  - `auth.envFile`: absolute path to the private setup-token env file

Declaring `auth` on a non-Claude agent is invalid config (`invalid_auth_agent`): the profile would never be enforced there, so it is rejected rather than silently ignored. A config whose `requiredEnv` or `forbiddenEnv` contradicts the automatic implicit environment contract for its agent — the agent-neutral process-integrity baseline for every supported agent, widened to the full Claude credential contract for `claude` and to the Codex executable-path contract (`CODEX_PATH` required) for `codex` — fails with `invalid_env_contract_overlap`; see [Environment preflight](#environment-preflight). Shape violations map to `invalid_auth`, `invalid_auth_kind`, `invalid_auth_env_file`, and `invalid_auth_env_file_not_absolute` with the invalid-config exit.

Optional:

- `model`: explicit ACP adapter model ID of at most 256 characters. For `agent: "codex"`, this must be the base model ID without a bracket suffix; omission resolves to `gpt-5.6-sol` (`CODEX_DEFAULT_MODEL`), and a historical composite such as `gpt-5.6-sol[medium]` fails closed as `codex_model_must_be_base_id`. After `ensureSession`, the supervisor applies the base value through runtime config option `model`; it does not pass the Codex model through `sessionOptions.model`. For `agent: "claude"`, the value remains the adapter-advertised ID and is passed through `sessionOptions.model`; bounded adapter-owned bracket forms such as `claude-fable-5[1m]` remain valid. The generic grammar is an alphanumeric start, then alphanumerics and `_ . : / @ + -`, optionally followed by one non-empty alphanumeric bracket suffix. Malformed forms fail as `invalid_model`. The namespace is the ACP adapter's, never OpenClaw's: a Claude model beginning with `anthropic/` fails as `invalid_model_openclaw_provider_key` before runtime loading, while canonical IDs such as `claude-fable-5` and `claude-opus-5` pass. A missing Claude model remains genuine omission and uses the public `runtime-default` label.
- `reasoningEffort`: Codex-only reasoning selection of at most 64 identifier characters. Omission on Codex resolves to `medium` (`CODEX_DEFAULT_REASONING_EFFORT`); presence on any other agent fails as `reasoning_effort_unsupported_agent`. After the base model acknowledgement, the supervisor applies this value through the adapter-advertised config option id `reasoning_effort`; `thought_level` is that option's category, not its `session/set_config_option` id, and `medium` is an advertised select-option value. Failure maps to `codex_reasoning_config_apply_failed`. The base `model` write maps failures to `codex_model_config_apply_failed`. Both writes must resolve before `startTurn`, so no ACP prompt can run with an unacknowledged selection. Public reporting derives the deterministic display identity `model[reasoningEffort]` — default `gpt-5.6-sol[medium]` — from the two validated fields; that composite value appears in reporting and the normalized `started` event but is never sent back as a runtime model. A Codex reporting bundle claiming `runtime-default` fails closed as `invalid_reporting_start_message`.
- `lifecycle.maxStartReceiptAgeMs`: receipt freshness window; defaults to `300000` and is bounded to `1000`–`3600000`
- `progressMs`: progress snapshot interval; zero disables snapshots
- `maxResponseBytes`: bounded response capture size
- `requiredEnv`: environment-variable names that must be present and non-empty in the supervisor's own environment
- `forbiddenEnv`: environment-variable names that must be absent or empty in the supervisor's own environment

## Start-receipt gate

`lifecycle` is required. It states that the caller already announced this run in the control conversation and supplies the delivery receipt for that announcement.

Identifiers are bounded decimal chat identifier strings of 1 to 32 digits; a JSON number is not a decimal spelling and is rejected rather than coerced. `deliveredAt` is a bounded ISO-8601 instant carrying at most six fractional-second digits and an explicit `Z` or numeric offset, so Discord's native `2026-08-22T07:47:48.530000+00:00` form is accepted as written; a local time without an offset is ambiguous and rejected, and a longer fraction is out of bounds. `lifecycle.startReceipt.conversationId` must equal `lifecycle.controlConversationId`, so a receipt earned in another conversation cannot start this run.

Shape violations are invalid config and keep the invalid-config exit mapping: `invalid_lifecycle`, `invalid_start_receipt`, `invalid_control_conversation_id`, `invalid_start_receipt_conversation_id`, `invalid_start_receipt_message_id`, `invalid_start_receipt_conversation_mismatch`, `invalid_start_receipt_delivered_at`, and `invalid_max_start_receipt_age_ms`.

Freshness depends on the clock rather than on the config text, so it is evaluated at run time before dynamic runtime import, runtime probing, `createAcpRuntime`, or any adapter startup. A receipt more than one second ahead of the supervisor clock fails with `start_receipt_future`; a receipt older than `lifecycle.maxStartReceiptAgeMs` fails with `start_receipt_stale`. The one-second forward allowance absorbs remote chat-clock skew and does not widen the freshness window. A config object that reaches `runSupervisor` without a bound, parsed receipt fails with `start_receipt_missing` or `start_receipt_conversation_mismatch`. That run-time check is a real backstop for configs assembled in memory instead of loaded from disk: it re-asserts string identifiers and the `1000`–`3600000` freshness bound rather than trusting or coercing them, so a numeric identifier or an out-of-range window fails with `start_receipt_missing`. These codes map to the supervisor error exit.

The gate validates caller-attested receipt metadata only. The supervisor holds no chat credentials and makes no network call, so it cannot prove that the message exists, that its text matches, that the caller authored it, or that the identifiers were not replayed from an earlier run within the freshness window. It proves that the caller committed to a specific, recent, same-conversation start message before the turn began.

The control conversation ID and the start message ID are never emitted in normalized events, stored in the response file, or hashed into any event field.

## Reporting contract

`reporting` is required. Current schema `acp-reporting-v3` binds one already-created ENABLED OpenClaw 2026.8.1 controller automation: isolated `{ "kind": "every", "everyMs": 600000 }`, deterministic `payload.kind: "script"`, 60-second timeout, five-call budget, exact ordered allowlist `acp_report_controller`, `message`, `automations`, `delivery: { "mode": "none" }`, and `deleteAfterRun: false`. The job must be created before the public start receipt; its exact returned ID is then bound as `reportPump.id`. The v3 config carries only the non-secret structural payload attestation (version, SHA-256 of the exact public placeholder script, timeout, budget, and allowlist), never the substituted script, lease token, private path/handle/snapshot, or a static report. Report content is derived freshly by the registered controller at each claim. Validation is pure and deterministic in `scripts/acp-reporting-contract.mjs`.

The contract is agent-neutral and binds to the canonical config `agent` through a closed, fail-closed presentation mapping: `claude` → `Claude Code`, `codex` → `Codex`. The ACP identity line of every template must carry exactly the mapped label for the run's canonical agent — the label is derived only from the mapping, never from caller data, so a run cannot present as another harness. An agent outside the mapping, or any non-canonical spelling of a supported agent, is rejected with `invalid_reporting_agent` before any template content is examined. An `acp-reporting-v2` bundle additionally carries a mandatory top-level `agent` attestation that must equal the canonical config agent; a mismatch is `invalid_reporting_agent`.

Schema compatibility is explicit and bounded. `acp-reporting-v3` replaces `watchdog`/`watchdogDestination` with `reportPump`/`pumpDestination` and requires the top-level `agent` attestation. `acp-reporting-v2` remains accepted unchanged for already-prepared disabled-watchdog configs; its transport binds the first claiming pump job. Legacy `acp-reporting-v1` remains accepted only for canonical `claude`; it carries no `agent` key, and v1 with any other agent fails `invalid_reporting_schema_version`. New preparations must produce v3. A v3 watchdog, `agentTurn` payload, announce delivery, extra payload field, wrong script digest/version, wrong timeout/budget, or wrong/misordered tool allowlist fails closed.

Ordering is pre-runtime: generate an opaque token privately; create the exact enabled script job and retain its ID; bind that ID and structural attestation into v3; send and record the public start receipt; assemble; `prepare` the exact transport; register the controller lease from the authenticated direct `main` owner session with its host-proven owner session/run, token, job, Discord account/destination, transport/handle, optional snapshot, and attested skill entry paths; require `prepared`; call transport `activate`; after `host_transport_activated`, call controller `commit_activation` and require `active`. Registration alone never authorizes the pump. `commit_activation` imports the attested host module and accepts only the exact closed `{ "schemaVersion":"acp-host-controller-lease.v1", "type":"host_transport_activation_confirmed", "processHandle":"<exact-handle>" }` proof returned from the durable activation-confirmed transport phase. The reporting bundle is validated during config loading and again by `runReportingPreflight` before runtime access. Stable failures are `invalid_reporting_context`, `invalid_reporting_agent`, `invalid_reporting_root`, `invalid_reporting_unknown_key`, `invalid_reporting_schema_version`, `invalid_reporting_round_index`, `invalid_reporting_repository`, `invalid_reporting_branch`, `invalid_reporting_start_message`, `invalid_reporting_destination`, `invalid_reporting_start_receipt`, `invalid_reporting_watchdog`, `invalid_reporting_watchdog_round`, `invalid_reporting_watchdog_schedule`, `invalid_reporting_watchdog_delivery`, `invalid_reporting_watchdog_payload`, `invalid_reporting_watchdog_message`, `invalid_reporting_report_pump`, `invalid_reporting_report_pump_round`, `invalid_reporting_report_pump_schedule`, `invalid_reporting_report_pump_delivery`, `invalid_reporting_report_pump_payload`, `invalid_reporting_report`, and `invalid_reporting_forbidden_content`; messages never echo rejected content or secrets.

On failure before authoritative activation confirmation, remove only the exact newly created automation first. If removal is confirmed and a prepared controller lease exists, call `abort_preactivation` and require `aborted`; never relaunch or fall back. The plugin imports the attested host module, whose `abortHostTransportPreactivation` serializes against activation, preserves the exact handle boundary, and returns only `{ "schemaVersion":"acp-host-controller-lease.v1", "type":"host_transport_preactivation_aborted", "processHandle":"<exact-handle>" }` after it has safely stopped and sealed a proven preactivation transport. Generic activation-in-progress state remains denied, including paste/write uncertainty. Its only abortable exception is an exact normalized sequence containing canonical `activation_required` followed immediately by one terminal bounded-code `supervisor_error`, with no activation confirmation, started/activity/progress/permission/terminal ACP evidence or malformed/mixed/out-of-order event; the exact session must be safely stopped or its exit must match supervisor-error code `22`. Activation-confirmed state, started or ACP evidence, post-activation terminal intent, malformed/unreadable state, and uncertain disappearance all deny abort. A mapped prepared-phase launcher exit and an already sealed exact abort are also safe. If automation removal fails, do not abort; if either cleanup step cannot be proven, retain the private state and fail `report_controller_pre_activation_cleanup_failed`.

If transport activation is confirmed but `commit_activation` fails or does not return `active`, removal and abort are both forbidden. Retain the exact owner-private `acp-report-controller-recovery.v1` / `commit_activation_pending` state shown in [templates/report-controller-commit-recovery.json](../templates/report-controller-commit-recovery.json), containing the token, job ID, transport file, and handle. From a fresh authenticated `main` run in the same canonical owner session, retry only `commit_activation`; the plugin re-derives host proof, and the operation is idempotent once active. Never remove, abort, relaunch, or infer activation failure in this branch. `scripts/acp-report-controller-preparation.mjs` makes the normal sequence, rollback ordering, and commit-only recovery executable through authenticated capability callbacks and never returns the token in its public result. Its exact job source is [templates/report-controller-automation.json](../templates/report-controller-automation.json), and the private register shape is [templates/report-controller-registration.json](../templates/report-controller-registration.json).

Start-message binding is caller-attested, like the start-receipt gate. `reporting.startReceipt` must byte-match the lifecycle receipt — same `conversationId`, same `messageId`, and the same `deliveredAt` spelling as written in `lifecycle.startReceipt` — and `reporting.startReceipt.message` must equal `reporting.startMessage`, so the attested delivery is bound to exact public content, not just to an identifier. This redundancy is deliberate: each field attests an independently prepared artifact or route, and the equality checks are the proof that they agree. Validation bounds match the supervisor's own config bounds — decimal identifiers of 1 to 32 digits, a model of at most 256 characters, a delivery instant of at most 40 characters. `startDestination`, `terminalDestination`, and the schema's pump/watchdog destination (`pumpDestination` on v3, `watchdogDestination` on v1/v2) must all equal `lifecycle.controlConversationId`: every reporting surface for the run is the one control conversation. The supervisor holds no chat credentials and makes no network call, so it cannot prove the message was actually delivered or that the pump automation (or legacy watchdog) actually exists in a scheduler; it proves the caller committed to specific, template-exact public content bound to the same recent control-conversation receipt that gates the run.

The canonical preparation path for `startMessage` is the production builder `buildAcpStartMessage` in `scripts/acp-reporting-contract.mjs`, exposed to operators as `scripts/acp-start-message-cli.mjs --input <absolute private JSON file>`. The builder derives the complete 13-line message — round title and mapped public harness label included — from structured inputs only (`agent`, `model` — omissible solely for `claude`, where it renders the literal `runtime-default` label; every other agent must state the run's effective model — `roundIndex`, `repository`, `branch`, an `HH:MM` `timeKst`, and the two free-text slots `scope` and `externalAction` as bullet content without the `- ` prefix), validates every field with the same fail-closed rules as the contract, and self-checks the rendered message through the same start-message validator, forbidden-content screen included. There is no title or label input: a `roundIndex` of 1 always renders the `🚀 ACP 작업 시작` title and any later round always renders the `🔁 ACP 수정 라운드 N 시작` correction title, so correction-round title drift is structurally impossible on this path. The CLI reads exactly one absolute owner-private JSON input file (no symlink, a regular file with no group or world permissions, bounded size), writes only the rendered public message to stdout, holds no chat credentials, and makes no network call; every failure emits exactly one `start_message_builder_error` event with a bounded stable code on stderr and the invalid-config exit, and never echoes the input path or any rejected free text. Hand-assembled start messages remain accepted when byte-identical to the fixed template — already-prepared supervisor configs stay valid — but new preparation must go through the builder.

Canonical lifecycle reports use `buildAcpIntermediateReport` and `buildAcpTerminalReport`, exposed by `scripts/acp-report-message-cli.mjs` with the structured templates [intermediate-report-input.json](../templates/intermediate-report-input.json) and [terminal-report-input.json](../templates/terminal-report-input.json). These builders derive the title, closed harness label, metadata order, phase name, terminal-status title, and every fixed section; caller-supplied title/label/template keys fail as unknown. Their model rule is identical to `buildAcpStartMessage`: Claude may omit `model` and renders `runtime-default`; every non-Claude agent must provide its explicit effective model and cannot claim `runtime-default`. `phaseIndex` must be an integer own property of the closed phase map, so prototype names and string numerals fail `invalid_reporting_report`. Completed terminal output is byte-exact with the established 20-line `🏁 ACP 완료 보고` contract: ACP identity, 작업, one `ACP 소요` line carrying the round, then `ACP 완료`, `ACP 자체 검증`, `결과`, `다음`, and `외부 작업`. Cancelled and failed terminal outputs have distinct titles and outcome headers and can never render the successful completion title. Both builders self-check the exact public layout and reuse the same metadata and forbidden-content validators. The start/report CLIs share the same normalized-path private JSON reader: stat and read target the same path, and missing, unreadable, empty, oversized, and invalid JSON inputs have distinct stable codes. The CLIs have no chat credentials and do not deliver messages.

The intermediate builder derives the ⏱️ time line from three independent structured integer minute counts — `totalMinutes`, `phaseMinutes`, and `lastAcpActivityMinutesAgo` — rendered exactly as `⏱️ **ACP 시간**: 전체 <N분> · 현재 단계 <N분> · 마지막 ACP 활동 <N분 전>`. `lastAcpActivityMinutesAgo` is the age of the transport boundary's `lastAcpActivityAt` (the explicit activity-age concept; the ambiguous `lastAcpStateChangeAt` name is deliberately not part of any schema), and each count is bounded, non-negative, and no larger than `totalMinutes` where coherence requires it. The 새 결과 bullet is derived from the integer `newResultDelta`, a value owned by the owner-confirmed reporting snapshot rather than the transport: it counts material ACP results completed since the previous successfully delivered intermediate report, the owner advances its semantic result cursor only after a verified delivery receipt, and it is never derived from raw tool-completion events — a completed read, edit, search, or command run is activity, not a material result. `0` requires `newResult` to be omitted and renders the canonical `Δ0 · 새로 확인된 ACP 결과 없음`, while a positive delta requires the free-text summary and renders `Δ<N> · <newResult>`. Δ and the activity age are independent by contract — `마지막 ACP 활동 0분 전` may coexist with `Δ0 · 새로 확인된 ACP 결과 없음`, and a newly completed material result increments Δ regardless of the activity age. The intermediate builder input shape is not a committed compatibility contract: the legacy free-text `elapsed` key (and any other unknown key) on intermediate input fails closed as unsupported. The terminal builder keeps its single free-text `elapsed` value for the `ACP 소요` line. Hand-assembled bundles validated under `acp-reporting-v1`/`acp-reporting-v2` keep the previous loose time-line check (a visibly non-empty `⏱️ **ACP 시간**: ` line), because those bundle schemas are committed contracts.

The public message formats are fixed, not advisory. `startMessage` must match the 13-line round-start template exactly and bind canonical agent/model/repository/branch identity. The v3 `reportPump` is exact-keyed: exact scheduler `id`, matching round, `enabled: true`, isolated 600000-ms schedule, deterministic script structural payload (`acp-report-controller-script.v1`, pinned placeholder-script SHA-256 `8e48a6cbe8bdb1e6142331257a5763edfc41687e9081745aea074a27146187e7`, timeout 60, budget 5, ordered allowlist), `delivery: { "mode": "none" }`, and `deleteAfterRun: false`. The actual script/token exist only in scheduler-private job state. The v2 watchdog retains its historical disabled, tool-less, bounded agentTurn snapshot shape solely for migration.

Free text is confined to the bounded slots — the 범위 and 외부 작업 bullets of the start message and the report's elapsed-time value, 실행 상태 value, and section bullets. (The elapsed-time slot is free text only where committed bundle schemas require it; the canonical intermediate builder derives its structured ⏱️ line from integer inputs and accepts no free-text time value.) Every slot must be visibly non-empty: C0 and C1 control characters, DEL, the U+2028/U+2029 line separators, and slots made only of zero-width or directionality format characters are rejected. A bounded forbidden-content screen runs over those free-text slots only, rejecting known operational patterns — filesystem paths, shell and Git commands, process or session inspection, scheduler internals, and known silence/self-decision phrasings — with `invalid_reporting_forbidden_content`. The screen is a fixed denylist of known patterns, a tripwire rather than a semantic filter: a novel paraphrase of silence or self-decision is not guaranteed to be caught, and the exact-template layout checks remain the primary control. Metadata lines are exact-matched against the validated `model`, `repository`, and `branch` values and are never screened, so ordinary names that merely contain a denylisted word — a `fix/routing` or `feat/cron-schedule` branch, a `snapshot-tool` repository — stay legal.

The fixed schema is generic and public: templates, cadence, routing shape, and screening are defined here and in the validator, with Korean public report layouts as the canonical wording. Organization-specific material stays outside the schema: actual channel identifiers, operator identity, and run-specific wording appear only inside the bounded free-text slots (the 범위 and 외부 작업 bullets, the section bullets, the elapsed-time and 실행 상태 lines) or as caller-substituted placeholder values, and none of it is emitted in normalized events.

## Environment preflight

`requiredEnv` and `forbiddenEnv` declare a generic caller-side environment contract. Each list is optional and bounded to 32 portable environment-variable names of at most 64 characters each, matching `[A-Za-z_][A-Za-z0-9_]*`. Contract-name identity is case-insensitive on every platform: Windows `process.env` lookups ignore case, so a case-conditional rule would make the same config mean different things per platform. Names that differ only by case are duplicates within a list, and required/forbidden overlap is judged case-insensitively. The caller's original spelling is preserved for environment lookup and for the sanitized failure codes. Shape violations are invalid config and keep the invalid-config exit mapping.

Before dynamic runtime import, runtime probing, `createAcpRuntime`, or any adapter startup, the supervisor fails closed when a required variable is absent or empty, or when a forbidden variable is non-empty. The stable failure codes name only the caller-declared variable — `required_env_missing:NAME`, `required_env_empty:NAME`, `forbidden_env_present:NAME` — and map to the supervisor error exit. Environment values are never emitted, stored, hashed, or otherwise disclosed.

Beneath the caller-declared contract sits an agent-neutral ACP process-integrity baseline, enforced automatically for every supported agent — `codex` exactly like `claude` — at the same pre-runtime point, even when `requiredEnv` and `forbiddenEnv` are empty or omitted. The baseline forbids the variables that can preload code into, redirect the module resolution of, or reroute the traffic of the supervisor process itself, independent of any provider: the Node.js module/preload selectors `NODE_OPTIONS`, `NODE_PATH`, and `NODE_REPL_EXTERNAL_MODULE`; the dynamic-linker preload/library selectors `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `DYLD_LIBRARY_PATH`, and `DYLD_FRAMEWORK_PATH`; and the proxy selectors `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY` in both upper- and lowercase spellings. A non-empty baseline variable fails closed with the same sanitized `forbidden_env_present:NAME` code and the supervisor error exit; an empty value cannot inject anything and passes. A config whose `requiredEnv` names a baseline variable — under any letter case — is contradictory and is rejected at load time with `invalid_env_contract_overlap`, for every supported agent, so a caller can never require an implicitly forbidden variable.

On top of the same baseline, canonical `agent: "codex"` carries an implicit Codex executable-path contract — the codex analogue of the automatic Claude credential contract, enforced by the supervisor at the same pre-runtime point (before dynamic runtime import, runtime probing, `createAcpRuntime`, or any adapter startup) even when `requiredEnv` and `forbiddenEnv` are empty, on both the config-file and in-memory paths. The operator launches a codex run with an explicit environment assignment naming the host's real Codex executable, for example `CODEX_PATH=/absolute/path/to/codex node acpx-foreground-supervisor.mjs --config …`; the value is host-specific operator configuration and never a constant in this skill (a current macOS Homebrew operator example is `/opt/homebrew/bin/codex`). A missing or empty variable keeps the sanitized generic codes `required_env_missing:CODEX_PATH` and `required_env_empty:CODEX_PATH`. A present value must be an absolute path of bounded length that resolves to an existing regular file with execute permission. Resolution deliberately follows symlinks, so a symlinked entrypoint such as `/opt/homebrew/bin/codex` stays valid while its target is a regular executable file. Violations fail closed with stable bounded codes on the supervisor error exit — `codex_path_not_absolute` (non-string, empty, over-length, or relative shape), `codex_path_missing` (nonexistent path), `codex_path_unreadable` (any other resolution failure), `codex_path_not_regular` (directory, FIFO, or other non-regular target), and `codex_path_not_executable` — and the path value is never emitted, hashed, or length-disclosed. A codex config whose `forbiddenEnv` names `CODEX_PATH` under any letter case contradicts the implicit contract and is rejected at load time with `invalid_env_contract_overlap`; restating it in `requiredEnv` is consistent and stays legal. This gate exists so a codex run can never silently bind to an implicitly resolved (for example transient npx-bundled) Codex installation. The exported guard keeps `codex_agent_not_canonical` as defense in depth for a non-canonical codex spelling when invoked directly, parallel to `claude_agent_not_canonical`.

The direct command above describes the supervisor child-process environment contract, not the production host invocation. Production callers place the same explicit `CODEX_PATH` assignment on the host transport CLI's `prepare` action; the private runner carries it into the canonical supervisor child without placing the value in the transport record.

The gate proves presence or absence only. It does not prove how a variable was injected, validate credential files, or select a credential source; for `codex` it proves the injected path names a real executable, not that the executable is a working Codex installation. For `agent: "codex"` the generic contract, the process-integrity baseline, and the executable-path contract are the whole environment gate. For `agent: "claude"`, credential-specific policy layers Anthropic-specific selectors and the setup-token contract on top of the same baseline and is canonical and supervisor-enforced; see [Claude credential injection](#claude-credential-injection).

## Claude credential injection

Claude runs authenticate with a setup token whose value is never disclosed: it does not appear in argv, config values, normalized events, error text, or logs, and no hash, prefix, suffix, or exact length of it is ever emitted. The config declares only a pointer: `auth.kind` fixed to `claude-setup-token-env-file` and an absolute `auth.envFile`.

The canonical route is `scripts/claude-acp-launcher.mjs --config <config>`. The launcher checks, in order:

1. CLI and config shape: it accepts exactly the same single private config-path argument as the supervisor and requires the canonical `agent: "claude"` (`launcher_agent_not_claude` for other agents, `invalid_agent_not_canonical` for a non-canonical Claude spelling; invalid-config exit).
2. Runtime support: a runtime or platform without a `process.execve` function fails `execve_unsupported`. This is checked before any environment or file inspection, so Windows and Node lines without execve always fail with this one code.
3. Clean-baseline parent environment; nothing is silently unset, the operator must remove offending variables explicitly:
   - a pre-existing `CLAUDE_CODE_OAUTH_TOKEN` — even empty — fails `claude_oauth_token_preexisting`;
   - any non-empty `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, or `CLAUDE_CODE_USE_FOUNDRY` fails `claude_competing_credential:NAME`;
   - any non-empty injection-capable variable fails `claude_env_injection_capable:NAME`. These are variables that could preload code into, redirect, or reconfigure the token-bearing supervisor image without appearing in its exec-argv proof. The list is the agent-neutral process-integrity baseline from [Environment preflight](#environment-preflight) — `NODE_OPTIONS` (`--require`/`--import` preloads), `NODE_PATH`, `NODE_REPL_EXTERNAL_MODULE`, the dynamic-linker preloads `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `DYLD_LIBRARY_PATH`, `DYLD_FRAMEWORK_PATH`, and the proxy selectors `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` in both upper- and lowercase spellings — plus the Anthropic-specific endpoint/header/config selectors layered on top for Claude only: `ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `ANTHROPIC_VERTEX_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS`, `CLAUDE_CODE_SKIP_BEDROCK_AUTH`, `CLAUDE_CODE_SKIP_VERTEX_AUTH`, and `CLAUDE_CONFIG_DIR`.
4. Env-file validation (below).
5. Exec-target pre-checks: a missing or non-executable Node binary fails `launcher_exec_target_missing`; a missing or unreadable supervisor file fails `launcher_supervisor_missing`.
6. The re-exec itself: the launcher replaces its own process image with POSIX `process.execve`, running `node --env-file=<auth.envFile> acpx-foreground-supervisor.mjs --config <config>` under the same PID, so no child wrapper or second tracked process ever exists.

Launcher failure contract: a failing `process.execve` raises a catchable system error in-process (it does not abort), which the launcher maps to the bounded code `execve_failed:<ERRNO>`. `execve_returned` is reachable only if an injected execve dependency returns instead of replacing the image or throwing. If the env file disappears between validation and the exec, the re-exec still succeeds and the replaced Node process fails its own `--env-file` startup parsing, exiting nonzero under the same PID before any supervisor code runs — fail-closed, with no launcher event, because the launcher image no longer exists at that point.

Launcher events: on failure the launcher emits exactly one `launcher_error` event — `{ schemaVersion, type: "launcher_error", code }` — and then exits. Unlike supervisor events it carries no run ID, request ID, sequence, timestamp, or elapsed time: no run identity exists before the supervisor starts, and the launcher never emits more than one event. CLI-usage and config-shape codes (`usage`, `invalid_*`, `launcher_agent_not_claude`) map to exit `64`; every later failure (`execve_unsupported`, `claude_oauth_token_preexisting`, `claude_competing_credential:NAME`, `claude_env_injection_capable:NAME`, `claude_env_file_*`, `launcher_exec_target_missing`, `launcher_supervisor_missing`, `execve_failed:<ERRNO>`, `execve_returned`) maps to exit `22`. On success the launcher emits nothing; the supervisor's `started` event is the first output of the same PID.

Env-file validation is shared by the launcher and the supervisor and fails closed on: a parent directory that is a symlink, not owner-owned, or not mode `0700`; a path that is a symlink (`claude_env_file_symlink`) or any non-regular file such as a FIFO or device (`claude_env_file_not_regular`, checked with `lstat` before open so a FIFO cannot block the validator); a file not owner-owned, not mode `0600`, empty, or oversized; and content that is not exactly one `CLAUDE_CODE_OAUTH_TOKEN=<value>` assignment with an optional final newline — no comments, quotes, interpolation, whitespace, extra variables, or multiline values. Filesystem errors on the env-file path map to distinct bounded codes: `claude_env_file_open_denied` (EACCES/EPERM), `claude_env_file_parent_not_directory` (ENOTDIR), `claude_env_file_symlink` (ELOOP/EMLINK), `claude_env_file_missing` (ENOENT), and otherwise the generic `claude_env_file_open_failed`. Failure codes (`claude_env_file_*`) never include the path, the file content, the token, a token hash, prefix, suffix, or the exact token length.

The supervisor independently re-asserts the same route before dynamic runtime import, probing, or adapter startup, so bypassing the launcher fails closed with the supervisor policy exit:

- the centralized closed-set agent gate runs first even for configs assembled in memory: any spelling that ACPX would normalize to a supported agent other than the canonical value fails `invalid_agent_not_canonical` — symmetric between `claude` and `codex` — and an agent outside the closed set fails `invalid_agent_unsupported`, both before the Claude route guard, the reporting backstop, and any runtime loading. The exported Claude route guard additionally refuses a non-canonical Claude spelling with `claude_agent_not_canonical` as defense in depth when invoked directly. Canonical `agent: "claude"` requires the auth profile (`claude_auth_missing`); an auth profile on another agent fails (`claude_auth_not_applicable`);
- `process.execArgv` must contain exactly one Node option, the exact spelling `--env-file=<auth.envFile>`; an absent or empty exec argv is a bare launch and fails `claude_env_file_option_missing`; every other shape — a split `--env-file <path>` pair, an `-if-exists` variant, a relative or different path, a duplicate, or any extra Node option — fails `claude_env_file_option_mismatch`;
- the Claude credential contract — `CLAUDE_CODE_OAUTH_TOKEN` required; the competing credential selectors and every injection-capable variable listed above (the agent-neutral process-integrity baseline plus the Anthropic-specific selectors) forbidden — is enforced automatically even when `requiredEnv` and `forbiddenEnv` are empty, with the same `required_env_missing`/`required_env_empty`/`forbidden_env_present` codes. A Claude config whose `requiredEnv` names any of these automatically forbidden variables is rejected at load time with `invalid_env_contract_overlap`;
- the env file is validated again and the loaded environment value is compared against the file assignment through fixed-size digests computed in memory and never emitted; a difference fails `claude_env_token_source_mismatch` without disclosing either value.

The digest comparison binds the loaded token value to the declared env file; it does not prove that the canonical launcher performed the injection, only that this process was started with the exact `--env-file` argv shape and that its token matches the declared file. What makes the route canonical is that every direct launch without that exact shape fails closed before runtime loading.

These are supervisor policy failures with exit `22`, evaluated before runtime loading. Invalid config shape remains exit `64`. Non-Claude agents are unaffected by the Claude route: they need no exec-argv proof and keep the generic environment contract — for `codex`, together with the executable-path contract from [Environment preflight](#environment-preflight), which is enforced at the same pre-runtime point.

## Permission decisions

Return only `allow_once`, `reject_once`, or `cancel`.

Reject:

- missing or unknown tool kind;
- tool kind outside `allowKinds`;
- missing, non-object, over-depth, over-width, oversized, or otherwise uninspectable structured raw input;
- an `execute` request that exposes no inspectable command;
- the unclassified `other` tool kind;
- explicit background or daemon flags;
- permission bypass settings or command-line flags;
- nested ACP or background-agent routes;
- `nohup`, `disown`, `setsid`, or standalone shell `&`;
- remote VCS actions reserved for the owner-side handoff: `git push`, `git send-pack`, `git lfs push`, Git aliases configured inside the turn, and every invocation of the repository-hosting CLIs `gh`, `hub`, or `glab`, including recognized shell and package-runner wrappers.

The shell rule is intentionally conservative. Use foreground parallel runners whose own process blocks until every child finishes.

The ACP implementation boundary is local-commit-only. Local inspection and commit commands such as `git status`, `git diff`, `git add`, `git commit`, and `git log` remain eligible for one-shot approval. After the ACP terminal result, the host owner independently verifies the diff, tests, and Git identity before performing any feature push or pull-request operation outside the ACP turn. The task prompt must explicitly stop the ACP agent after its local commit and prohibit delegating a remote action to a script.

This remains a permission-layer contract, not an operating-system network sandbox. It rejects the inspected request shapes above; it cannot prove that an otherwise allowed opaque program has no remote side effect. Do not describe it as network isolation.

## Event identity

Assign one supervisor run ID and one request ID. Bind them to one ACP turn.

Every normalized event includes:

- schema version;
- supervisor run ID;
- request ID;
- monotonic sequence;
- timestamp;
- elapsed milliseconds;
- event type.

Never merge multiple turns under one run ID.

## Evidence boundary

The event stream provides activity evidence, not terminal evidence.

Normalize event payloads. Allow only bounded protocol-token forms for tags, tool kinds, tool status, runtime versions, stop reasons, and error codes. Drop or replace everything else. Do not emit raw prompt text, raw model text, raw tool input, raw tool output, content blocks, tool titles, secrets, tokens, or unrestricted command output.

A timer-driven progress event is a snapshot. `evidenceAgeMs` exposes the age of the last actual ACP event so consumers do not mislabel an old snapshot as fresh activity.

`activation_required` and `activation_confirmed` are host-control events, not ACP activity evidence. They contain no process handle. Only the matching turn `result` determines ACP terminal state. A successfully emitted `terminal` or `supervisor_error` event closes normalized output; no later ACP activity is delivered. Terminal events omit the working-directory name and response fingerprint.

## Stable exits

- `0`: completed
- `20`: cancelled
- `21`: failed
- `22`: supervisor policy, environment preflight, compatibility, deadline, runtime, storage, stream, cleanup, or delivery error

When the ACP result is exact but response storage, event draining, cleanup, or response completeness is degraded, preserve the exact ACP status in the terminal event, set `supervisorStatus: "degraded"`, and exit 22.

One bounded capability exception applies to cleanup. The Codex ACP adapter does not implement the `session/close` backend control, so the terminal `discardPersistentState` close is rejected by the runtime with its structured `ACP_BACKEND_UNSUPPORTED_CONTROL` error code even though the turn itself succeeded. Exactly when the canonical agent is `codex`, the session mode is `oneshot`, an exact `completed` result has been received, the event stream drained cleanly, and the captured response is untruncated, the supervisor treats that one structured rejection as a capability signal instead of a cleanup failure: it emits a `cleanup_unsupported_close_fallback` activity and retries `close` once without requesting backend persistent-state disposal, which still cancels and closes the local runtime handle deterministically. When the fallback close succeeds, `cleanupOk` stays true, the terminal event records `cleanupFallback: true`, and the run keeps its exact mapped exit. Detection uses only the runtime's structured error code — never message text — and a close timeout is not an unsupported-control signal. If the fallback close itself fails or times out, `cleanupOk` becomes false, the terminal event stays `supervisorStatus: "degraded"`, and the run exits 22. Every other case keeps the fail-closed contract unchanged: every other agent (including `claude`), every non-`completed` result, every other cleanup error or timeout, and the catch-path cleanup after a supervisor error always request the canonical persistent-state discard and fail closed on any cleanup error. Response storage remains authoritative and happens after cleanup, so a failed response write still degrades the run to exit 22 even after a successful fallback close.
- `64`: invalid CLI or config

After `main()` resolves, the CLI bounds stdout/stderr flushing and then exits with the mapped code. A leaked adapter handle must not keep the foreground caller waiting after terminal evidence has been delivered.

Do not collapse cancellation or failure into success.

## Host activation and lifecycle ledger

The supervisor starts in `activation_required` and creates its owner-private lifecycle ledger before importing ACPX. Production ownership is provided by `acp-host-transport-cli.mjs`: a `prepare` call creates one private transport record and tmux session, starts the supervisor inside that PTY, and returns its exact non-empty session handle without activating ACP. Only a later `activate` call that presents the same private record and exact handle writes one newline-terminated activation record into that PTY:

```json
{"schemaVersion":"acp-host-activation.v1","processHandle":"<exact-host-handle>"}
```

The record is bounded to 512 bytes, has exactly those two keys, and accepts only a 1–128 character process-handle token composed of alphanumerics plus `. _ : -`. The default activation deadline is 60 seconds so the bounded `prepare` result can return to the owner before the separate `activate` call. EOF, timeout, stream error, malformed JSON, unknown keys, a wrong schema, or an invalid handle fails closed before runtime import with `activation_eof`, `activation_timeout`, `activation_input_error`, `activation_invalid`, or `activation_invalid_process_handle` and exit 22. The handle value is stored only in the private ledger and is never included in normalized events.

The transport record, event file, stderr file, environment snapshot, and mapped-exit file live in the owner-only state directory. The runner removes its private environment snapshot after spawning the canonical entry point. The tmux session explicitly clears known injection variables and starts the runner through `/usr/bin/env -i` with only a bounded operational environment; the child receives caller-declared required values from the private snapshot, never from tmux-server residue. `status` validates and bounds normalized event output; callers do not read those files directly. `cancel` sends Ctrl-C only to the exact retained PTY. `probe` must pass before the public start boundary so an absent tmux or clean-environment capability cannot create a false started report.

The transport record also owns the fail-closed publication protocol. Two mechanisms compose, and neither substitutes for the other. First, every record mutation — `status`, `claim-report`, `begin-delivery`, `ack-report`, `reconcile`, `cancel`, and the `activate` anchor write — runs under an exclusive sibling lease file (`<record>.lock`): the lock serializes the whole read-modify-write critical section with a bounded wait (`host_transport_lock_timeout` on expiry), and a live lease is never silently stolen — only a lease older than the stale age (a crashed holder) may be taken over. Atomic sibling-temp-plus-rename replacement is retained, but it only prevents torn files; it is never described as serialization. Second, a monotonically increasing publication fence orders the long-lived attempts that span multiple calls: every claim increments `fence` and mints one attempt identity, and a superseded (stale-fence) claimer can neither begin delivery nor acknowledge (`host_transport_report_fencing_stale`).

Observation and publishing are separated. `status` is observation-only: it returns bounded evidence, the stored publication boundary (with its explicit `deliveryState`), and service cursors, but it never mints, supersedes, or re-claims a report obligation. The closed `claim-report` action is the only minting path: under the lease it verifies the exact handle, the exact control-conversation `destination`, and the bound scheduler job identity (`host_transport_pump_destination_mismatch`, `host_transport_pump_job_mismatch` — a v3 config binds `reportPump.id` at prepare; a legacy v1/v2 record binds the first claiming job), derives the fresh canonical intermediate or terminal boundary from the current normalized evidence, records one fenced publication attempt, and returns only the bounded data needed for delivery (attempt/fencing identity, report identity, kind, cadence, required instant, public reporting identity, and `lastAcpActivityAt` or terminal status/elapsed). Delivery states are explicit: `claim_acquired` on claim, `delivery_pending` after the separate `begin-delivery` action persists the handoff, `acknowledged` on receipt acknowledgement, and an explicit `uncertain` or `missing` last-attempt outcome when a newer claim supersedes an expired attempt — `uncertain` when the crash happened after the Discord handoff (`delivery_pending`; success is never inferred), `missing` when no handoff was ever persisted (`claim_acquired`; safe retry). A live attempt within its bounded TTL blocks re-claiming (`host_transport_report_claim_held`), and attempts per report obligation are bounded (`host_transport_report_attempts_exhausted`).

The activation-confirmed event binds the supervisor's original elapsed-time origin, and the first intermediate becomes due at exactly ACP elapsed 600,000 ms rather than 600,000 ms after the activation call. A `claim-report` at or after that instant mints the intermediate obligation and freezes the evidence boundary; later polls cannot return a newer sequence until `ack-report` accepts the matching identity, kind `intermediate`, cadence, the exact `attemptId` and `fence` of the live `delivery_pending` attempt, exact control-conversation destination, 1–32 digit decimal message ID, and a delivery instant at or after the requirement with one of the closed successful statuses: `"sent"` for a direct source send or `"delivered"` for the isolated controller's hook-confirmed message delivery. The caller-attested delivery instant preserves the documented bounded ISO-8601 wire spelling: an explicit `Z` or numeric offset and at most six fractional-second digits, including Discord forms such as `2026-08-22T07:47:48.530000+00:00`. Because it comes from a remote chat-provider clock, receipt freshness accepts only a symmetric one-second skew around the host boundaries: no earlier than one second before the required instant and no later than one second after the current host instant; the five-minute receipt-age limit remains fail-closed. Private transport-generated timestamps (`createdAt`, cadence anchors, publication requirements, attempt instants, and `controlCursorIssuedAt`) remain canonical millisecond UTC strings generated by `Date#toISOString`. `ack-report` also carries the exact structured report and a `messageDigest`: the transport checks its stored agent/model/round/repository/branch identity — for Codex, the same deterministic `model[reasoningEffort]` public identity used by start/report builders and the normalized `started` event — re-runs the matching canonical builder, binds terminal status when applicable, and requires SHA-256 of that exact canonical string (excluding the report CLI's final stdout newline). Canonical construction is therefore machine-enforced. No current obligation fails `host_transport_report_not_required`; retrying an already acknowledged identity fails the distinct `host_transport_report_ack_duplicate`; an acknowledgement whose attempt never persisted the `delivery_pending` handoff fails `host_transport_report_ack_state`. Acknowledgement releases the attempt lease deterministically (`attempt` cleared, outcome `acknowledged`, attempt budget reset). Acknowledged message IDs remain private, unique, and bounded to the most recent 64; a reused message ID fails the distinct `host_transport_report_receipt_duplicate`. A valid late intermediate acknowledgment advances from the prior due anchor in one transition past all already-missed anchors, returns the bounded `skippedCadences` count, and schedules the first future cadence while ACP `elapsedMs` continues from the original supervisor start.

An intermediate `reportPublication` boundary additionally carries one derived value, `lastAcpActivityAt`: the timestamp of the latest normalized ACP activity event of the exact execution handle (envelope type `activity` — the model/tool/status activity events). It is recomputed from the append-only event log on every status, so it only moves forward with new ACP activity events and is never reset by a transport poll boundary, report rendering or delivery receipt, phase bookkeeping, or owner-side work — timer-driven `progress` bookkeeping does not move it either. Host lifecycle/control marks (`activation_confirmed`, `started`) are not ACP activity and never substitute for it: with no normalized ACP activity event yet, `lastAcpActivityAt` is a fail-closed `null`. The boundary exposes no Δ result count and the transport record keeps no result cursor, because the transport sees only raw normalized events and cannot classify material result artifacts — a completed read, edit, search, or execute tool event is activity, never a material result. The Δ in the public 새 결과 bullet is owned by the owner-confirmed reporting snapshot: `newResultDelta` counts material ACP results completed since the previous successfully delivered intermediate report, and the owner advances that semantic result cursor only after a verified delivery receipt, so ACP activity without a newly completed material result keeps `Δ0` while `마지막 ACP 활동` stays fresh, and a newly completed material result increments Δ independently of the activity age.

A matching normalized terminal event supersedes an overdue intermediate atomically. The terminal `claim-report` mints terminal cadence 0 before `ack-report` — recording the interrupted intermediate attempt's explicit uncertain/missing outcome under a fresh fence — and an intermediate identity or stale fence can no longer acknowledge it. Terminal before the first cadence creates no intermediate obligation. When supersede exposes terminal sequence N beyond a frozen evidence boundary, `lastSequence` advances only through the consecutive evidence actually returned; it never jumps over hidden evidence merely because terminal N was delivered out of order. After terminal receipt acknowledgement lifts the boundary, the next status returns the skipped gap and can then advance the cursor through it. Mapped exit evidence before terminal acknowledgement does not mutate the lifecycle ledger: reconcile returns `terminal_publication_pending`; only canonical terminal receipt acknowledgement permits private exit reconciliation. Receipt conversation IDs, message IDs, digests, delivery instants, report IDs, attempt IDs, fences, leases, pump job IDs, service cursors, and process handles never enter normalized events or public report text, and receipt identifiers are not echoed by `ack-report`.

Every successful `status` also issues one private control-service cursor. The next `status` must carry exact-key `serviceCursorAck` with that cursor, the exact control conversation, and a fresh `servicedAt` not before cursor issuance. `serviceCursorAck.servicedAt` is owner-clock attestation, not a chat-provider receipt: it must use the canonical millisecond UTC spelling generated by `Date#toISOString` and is measured against the host clock, so it does not accept the remote receipt offset/microsecond spelling. If a status response is lost, a call with `reissueServiceCursor: true` returns the same current cursor without replacing it, at most three times and only inside the five-minute cursor window; acknowledgement remains exact. This is an enforceable caller-attestation gate against a tight polling loop starving newly steered user input; it is not a Discord network proof. The transport has no chat credentials and cannot verify that the caller actually fetched or answered a message.

The ledger schema is `acp-host-lifecycle.v1`. It records the supervisor run/request IDs, exact process handle, activation time, latest durably sampled normalized event, terminal intent, and expected mapped exit. High-rate `activity` events are persisted at most once per second; control, progress, started, permission, terminal, and supervisor-error events flush immediately. A terminal event is still not a confirmed host exit: the ledger remains `terminal_intent` with exit reconciliation pending.

After the exact tracked handle returns its process exit, the caller writes an owner-private JSON input containing `ledgerFile`, the same `processHandle`, `outcome: "exited"`, and the mapped `exitCode`, then runs:

```bash
node /absolute/path/to/acp-discord-orchestrator/scripts/acp-lifecycle-reconcile-cli.mjs --input /absolute/private/reconcile.json
```

The reconciliation CLI requires a private non-symlink input file, verifies handle and exit-code equality against the ledger, and then records `exit_reconciled`. Repeating an already-confirmed exit re-verifies the current handle, outcome, and mapped exit against the stored reconciliation and returns the unchanged ledger only on an exact match. Repeating `tracking_lost` likewise returns that precise stored outcome; attempting to reinterpret it as an exit fails `lifecycle_tracking_lost`. A mapped supervisor exit before activation is the only null-handle ledger case: the caller must provide explicit JSON null, terminal intent and mapped exit must match, and the ledger remains visibly unactivated. Supplying an invented handle fails `lifecycle_handle_unexpected`. A Claude `launcher_error` occurs before any supervisor ledger exists; the host transport reconciles that bounded terminal record directly with its exact mapped exit (`22` or `64`) and returns `pre_activation_exit_reconciled`. When an activated exact handle is dead and no terminal intent exists, the caller instead supplies `outcome: "tracking_lost"` with no exit code; an unactivated ledger can never become tracking loss. A terminal intent cannot be rewritten as tracking loss, a missing terminal cannot be reconciled as success, and a mismatched handle or exit code fails closed. Completion requires both the matching normalized terminal event and the mapped exit, followed by canonical terminal receipt acknowledgement and private-ledger reconciliation. `tracking_lost` never authorizes automatic success or automatic relaunch.

## Report publication pump

Intermediate and terminal reporting is coreless: it does not depend on the direct owner turn repeatedly calling `status`. One ENABLED every-600000-ms OpenClaw automation per exact ACP handle runs the exact deterministic script in [templates/report-controller-automation.json](../templates/report-controller-automation.json). The actual scheduler job substitutes only its private lease token. From the authenticated isolated `cron:<jobId>` session, the script calls `acp_report_controller(action:"tick")`; the controller validates the job/session/lease, revalidates content attestations, imports `scripts/acp-report-pump.mjs` and `scripts/acp-host-transport.mjs` in-process, and returns a declared structured result.

On `delivery_pending`, the script passes the returned message byte-for-byte to `message(action:"send", final:false)` using the returned registered Discord channel, account, and conversation, then performs one bounded second tick. OpenClaw 2026.8.1's `message_sent` hook supplies the authoritative success and message ID; the controller derives the Discord instant and calls the transport's fenced acknowledgement itself. Its closed `outputSchema` describes every success, quiet, pending, cleanup, and error result, and Code Mode projects the structured `details` object directly, so the script does not parse tool-result prose. `delivery.mode: "none"` prevents a runner fallback/static announcement.

No static public report snapshot is ever the reporting source: the report kind, cadence, terminal status, cadence-derived minutes, and the `마지막 ACP 활동` age are machine-derived from the live claim at pump time. Bounded owner-maintained free-text slot content may come from an optional private structured snapshot file (schema `acp-report-pump-snapshot.v1`, template [templates/report-pump-snapshot.json](../templates/report-pump-snapshot.json)); omitted slots render fixed neutral defaults, an unknown or malformed snapshot fails closed (`report_pump_snapshot_invalid`) before any claim is minted, and no snapshot value can move a machine-derived time, cadence, or status. Without a normalized ACP activity event the activity age renders the fail-closed maximum (the whole elapsed run), never a fabricated fresh instant.

Non-claim outcomes are closed and deterministic: `none_due`, `delivery_missing`, `delivery_uncertain`, and `error` stay silent. For `terminal_acked` or `tracking_lost`, the script removes only `result.jobId` through the cron run's host-enforced self-removal scope, then releases its lease; removal failure prevents release. `tracking_lost` never relaunches ACP. The lease token, controller identities, receipts, handles, and paths never enter public output.

The controller owns cadence publication, not the remaining completion proof. Owner-side mapped-exit observation, response inspection, lifecycle-ledger reconciliation, and Git/PR verification remain required and may resume later from the exact retained private record in the registered canonical owner session. The plugin blocks `sessions_yield` and final messages for the exact active owner run and requests `before_agent_finalize` revision with `maxAttempts: 2`, but OpenClaw's budget is bounded and `agent_end` is observational. After the host exhausts that budget the plugin cannot cancel finalization; it logs a violation and keeps the durable lease so the cron controller continues. This is persistence, not an indefinite owner-run guarantee.

## Process liveness

Session existence, adapter process existence, supervisor process existence, child-shell existence, and Discord typing state do not prove that the ACP turn is still active.

Their disappearance also does not replace the exact turn result. `active + dead exact handle + no terminal intent` is a `tracking_lost` control-plane fault, not ACP success, failure, or cancellation.

## Host wait boundaries

Foreground ownership is a property of the supervisor and adapter inside the transport PTY, not of the caller's one-shot shell call. The caller may return from a host tool while the tmux-owned supervisor keeps running, provided every later operation presents the same private transport record and exact session handle.

The caller contract is:

- run a harmless transport `probe` before publishing the start boundary;
- call `prepare` once and retain the exact non-empty process handle and private transport record it returns;
- call `activate` separately with those exact values, and require both `host_transport_activated` and `activation_confirmed` before ACP runtime mutation;
- when actively supervising, poll only the transport `status` action with those same values, waiting 1, 2, 4, and then 5 seconds, and acknowledge each returned service cursor after servicing steered input; cadence publication itself requires no owner polling;
- retain the exact private preparation record so mapped-exit and ledger reconciliation can resume later in the same canonical owner session if the bounded finalize guard does not keep the original run alive; while actively supervising, continue the retained round unless the message explicitly cancels or replaces it;
- let the round's enabled report-pump automation claim, deliver, and acknowledge every required intermediate report through `claim-report`/`begin-delivery`/`ack-report` before evidence advances past its boundary; let terminal supersede an overdue intermediate;
- report completion only after the matching normalized terminal event, mapped process exit, private-ledger reconciliation, and canonical terminal-report receipt acknowledgement.

In other words, completion requires both the matching normalized terminal event and the mapped process exit, plus successful reconciliation and the acknowledged canonical terminal receipt.

One run has one transport record and one handle. Do not open a second transport, use a PID search, poll transcripts or raw files, run a broad process monitor, use a long shell sleep, or add a nested wrapper for the same run.

A returned poll is evidence about the host boundary only. It is not activity evidence, and it is never terminal evidence. Bounded host waits change when the caller regains control; they do not change the evidence boundary, stable exits, or cancellation. If a later owner run observes a dead/missing handle without terminal intent, reconcile `tracking_lost` once; the registered controller independently stops publication and removes only its current job before release.

## Cancellation

Bind SIGINT and SIGTERM before runtime probing, carry a pending request into the exact turn once it exists, and release handlers only after normalized terminal output and cleanup. Continue waiting for the exact result until the required deadline and bounded cancellation grace expire. Do not report `cancelled` merely because a signal handler ran.

## Non-goals

This contract does not:

- globally disable OpenClaw ACP commands;
- provide an operating-system sandbox;
- read, authenticate, or otherwise confirm a chat message from the supervisor process;
- guarantee containment of arbitrary foreground code that daemonizes internally;
- leave the report-pump cadence (or legacy watchdog interval), destination routing, or public message templates caller-defined — the [Reporting contract](#reporting-contract) fixes them generically, and only the bounded free-text slots plus the actual (organization-private) channel identifiers vary per run;
- prove that the attested start message, report-pump automation, or legacy watchdog snapshot exists outside the config;
- discover or reconstruct a lost host handle from a PID, transcript, or process search;
- make an official ACP child thread observable by the direct supervisor.
